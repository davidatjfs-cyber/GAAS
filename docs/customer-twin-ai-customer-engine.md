# AI 顾客引擎设计（岗位教练技能化改造核心）

> 版本：v1 草稿（2026-08-07）｜状态：待评审
> 目标：14 项前厅技能全部以"客人视角情景会话"训练，单次会话目标 ≥10 分钟；
> 打分可靠（规则 + LLM 裁判 + 每日校准），升级规则 10 次/7 成功。

## 一、为什么不能沿用现状

现状 AI 顾客 = 规则状态机（store-tracks），只能撑 2-5 分钟短客诉；
技能化后需要：多阶段长会话、按技能定制人设、知识库驱动追问、多维可靠打分。

## 二、总体架构

```
技能剧本（14 技能 × 剧本：人设/开场/深挖/挑战/收尾）
  +
知识库（11 份手册按章节入库 + 真实客诉卡 + 菜品库属性）
  ↓
AI 顾客会话引擎
  ├─ 会话管理（阶段状态机）
  ├─ 人设与话术生成（LLM，受剧本+知识约束）
  ├─ 知识检索（RAG：客人提问依据 + 员工回答核对）
  └─ 时长与目标控制（维度覆盖 + 自然深度）
  ↓
会话记录（完整对话 + 锁定事实 + 技能 + 剧本版本）
  ↓
评分
  ├─ 规则层：关键原则检测（一票否决）
  ├─ LLM 裁判：按维度结构化打分 + 引用对话原文
  └─ 校准层：每日随机 1-2 条 → 管理员工作台 → 一致率 ≥85%
  ↓
进度与升级（10 次 / 7 成功，普通→高级→金牌）
```

## 三、会话管理（阶段状态机）

每个技能会话按 4 阶段推进，AI 顾客在每个阶段有明确目标：

| 阶段 | 目标 | 示例（菜品知识技能） |
|---|---|---|
| 开场 | 建立场景、抛出第一个问题 | "服务员，你们豆酱焗鸡用的哪里的鸡？" |
| 深挖 | 连续追问、覆盖考核维度 | "豆酱是什么味道？""为什么鸡这么嫩？" |
| 挑战 | 增加难度：质疑/对比/换问题 | "我上次在别家吃的不是这个味，你们正宗吗？" |
| 收尾 | 自然结束 | 对回答满意/不满意 → 决定是否复购/投诉 |

规则：
- 每个阶段至少要完成 **2 轮有效问答**才进入下一阶段；
- 全部 4 阶段走完 = 会话结束，目标时长 ≥10 分钟（按轮数与深度达标，不硬卡秒数）；
- 会话中员工若触犯关键原则（如客诉先安抚被违反），AI 顾客按剧本升级情绪；
- 同一员工同一技能连续会话不重复使用同一剧本种子（防套路）。

## 四、技能剧本（14 项）

每技能一份剧本 JSON：

```
skill_key / 客人人设（年龄/性格/目的）/ 场景（时段/人数/情境）
开场问题池（≥5）/ 深挖问题池（≥10，按考核维度分组）
挑战问题池（≥5）/ 收尾逻辑（满意→复购承诺；不满意→投诉/差评）
考核维度（对应打分维度）/ 关键原则（一票否决）
```

示例（推销·充值）：
- 人设：常客，价格敏感，犹豫要不要充；
- 开场："你们会员充 500 送 100 是真的吗？"
- 深挖："我一个月就来两三次，划算吗？""充了能用在套餐上吗？"
- 挑战："上次充了感觉没优惠，你们是不是套路？"
- 收尾：员工促成成功 → 客人接受；失败 → "我再想想"。

## 五、知识检索（RAG）

- 11 份手册按章节入库（96 条，技能标签），真实客诉卡、菜品库属性并行接入；
- AI 顾客提问：从剧本问题池出发，**回答正确性依据由知识库提供**（豆酱焗鸡产地必须来自知识库，不能编）；
- 员工回答核对：LLM 裁判打分时，用 RAG 检索对应知识条目核对"知识准确性"维度；
- 事实闸门：员工回答含"大概/好像/应该是"等模糊表述 → 规则层扣分。

## 六、打分体系（三层）

**规则层（确定性）**：关键原则检测（每技能 3-5 条，一票否决）＋事实闸门＋时长/轮数完整性。

**LLM 裁判层**：
- 输入：完整对话 + 技能剧本（含考核维度与标准）+ RAG 命中知识条目；
- 输出：结构化 JSON：每维度分数（0-100）+ 依据（引用原文哪一句）+ 总评 + 是否触发否决项；
- 温度低、固定提示词版本，输出可追溯。

**校准层**：
- 每日随机抽 1-2 条当日会话 → 管理员工作台任务卡（完整对话，隐藏 AI 评分）→ 管理员逐维度打分提交 → 显示 AI 评分对比 → 入库校准记录；
- 一致率 ≥85% 才正式启用该技能评分；不一致条目进校准清单。

## 七、进度与升级

- `job_coach_skill_progress`：每人每技能（级别/训练次数/成功次数）；
- 成功 = 本次得分 ≥80 且无关键原则违规；
- 升级 = 当前级内 训练次数 ≥10 且 成功次数 ≥7；升级后重新计次；
- 同卡 7 天内重复不计训练次数；抽卡按技能内随机+近期去重。

## 八、与现有系统集成

- 复用：sales_sim_sessions（会话表）、job_coach_incident_cards（卡）、知识库、评分/复盘前端；
- 替换：store-tracks 规则顾客 → 剧本+LLM 顾客（可配置开关，先灰度 1 个技能验证再全量）；
- 保留：真实客诉卡（归类到堂食客诉/外卖客诉技能）、培训卡审核流程、每日自动生成。

## 九、实施顺序（草稿）

1. 知识库导入（dry-run 已出，待确认后接 knowledge_base）；
2. 迁移 181（技能/进度/卡归类，待评审）；
3. 会话引擎 v1：先做 1 个技能（堂食客诉或推销）完整剧本 → 灰度试点 → 校准一致率达标 → 扩展到 14 技能；
4. 前端技能墙 + 进度/升级展示；
5. 每日校准任务上线。

## 十、风险与边界

- LLM 长会话可能漂移 → 剧本约束 + 阶段机 + 低温度 + 版本化；
- LLM 打分不可靠风险 → 校准层是硬门槛，不达标不启用；
- 知识库内容决定提问质量 → 菜品知识卡后续补；
- 10 分钟目标是体验目标，考核以"维度覆盖 + 自然深度"为准。
