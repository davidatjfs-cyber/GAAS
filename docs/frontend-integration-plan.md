## 1. 门店红绿灯——确切定义

**数据来源**：`server/domains/store-scoring/store-rating.js` 的 `calculateStoreRating()`，已经在跑，每月计算一次，落库 `store_ratings` 表。

**确切算法**（不是我编的，是这段代码本身）：
```
达成率 = 当月实际营收（daily_reports 汇总）÷ 当月目标营收（revenue_targets 表）
达成率 > 95%  → A
达成率 > 90%  → B
达成率 ≥ 85%  → C
其余          → D
没设目标营收   → rating = null（无法评级）
```

**红绿灯映射**（本次确认）：
```
A / B  → 绿
C      → 黄
D / 无评级 → 红
```

**局限性，必须让你知道**：这**只是营收单指标**，不包含差评、人效、任务积压。如果某家店营收达标但差评很多/人效很差，红绿灯依然显示绿色。这是本次刻意的取舍（多指标综合会显著增加工作量），后续如果你觉得不够用，可以再加维度，但那是新的开发量，不是这次范围内。

**实现方式**：`server/domains/workspace/service.js` 里新增一个函数，直接查 `store_ratings` 表最新一期的 `rating` 字段做映射，取代我之前那版"有没有开放任务"的占位逻辑。

## 2. 决策回执——确切流程

**适用范围**：只针对"经营决策类动作"——那些**批准之后没有人工验收步骤、需要等一段时间看数据变化**才能判断有没有效果的动作。具体是：
- 召回/唤醒类营销动作（`growth/actions/:actionKey/execute` 这类）
- 新品/动作批量推广到多店（我们已经做的 `promote-dish` 接口）

**不适用**：普通任务指派（`master_tasks`）——见第4节详细解释为什么。

**天数**：
| 动作类型 | 首次回执天数 | 看什么指标 |
|---|---|---|
| 召回/唤醒营销 | 7天 | 触达人数、回店人数、回店率、归因营收 |
| 新品/动作推广 | 14天 | 各店该菜品/动作的销量变化 |

**持续跟踪机制（这次新确认的设计）**：

```
[老板批准动作]
      ↓ 记录到 decision_receipts 表：{actor, action_type, ref_id, decided_at, next_check_at}
      ↓ 等待 next_check_at（7天或14天后）
[系统自动生成第一次回执卡片]
  "你7天前批准的召回：触达1247人，回店96人，回店率7.7%，归因营收¥9.2万"
      ↓ 卡片带两个按钮
   [结束跟踪]                    [继续跟踪]
      ↓                              ↓
   receipts.status='closed'    生成新的 next_check_at（+7天或+14天，按原动作类型）
                                     ↓
                              到期再生成下一轮回执卡片，循环
                              （不限次数，直到用户选"结束跟踪"或活动本身状态变成已结束）
```

**表结构**（Phase 3 新建）：
```sql
CREATE TABLE decision_receipts (
  id BIGSERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  actor_username TEXT NOT NULL,
  action_type TEXT NOT NULL,        -- 'recall_campaign' | 'dish_promotion'
  ref_type TEXT NOT NULL,           -- 关联对象类型
  ref_id TEXT NOT NULL,             -- 关联对象ID（campaign_id / promote任务的task_id集合）
  decided_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  next_check_at TIMESTAMPTZ NOT NULL,
  round_no INT NOT NULL DEFAULT 1,  -- 第几轮跟踪
  status TEXT NOT NULL DEFAULT 'pending', -- pending | shown | continued | closed
  last_result_snapshot JSONB,
  tenant_id_check CHECK (tenant_id <> '')
);
```

## 4. 普通任务怎么指派的——你问的这个我如实说明

**现状机制**（`server/domains/master-agent/resolve-assignee.js`）：

1. **绝大多数任务是系统按规则自动指派的**，不是"随便指派给任何人"：
   - 厨房/出品类问题（比如"桌访产品异常"）→ 只能派给**出品经理**
   - 服务/前厅类问题（比如"服务差评异常"、"充值异常"）→ 只能派给**店长**
   - 按门店名匹配到具体那家店的负责人
2. **也支持人工改派**（`/api/agent-task-board/tasks/:taskId/reassign`），但这个接口本身**没有限制"只能改派给谁"**——权限校验在 agents-service-v2 那边（不在我这次能看到/改的 GAAS 仓库里），我没法从这边确认它是不是也限制了"只能改派给同店/同角色的人"还是真的能派给任何人。**这一点我需要老实说：我不确定，需要去查那个服务的代码才能给你准确答案**，如果这对你很重要，我可以下一步专门去查。

**为什么普通任务不需要决策回执**：任务本身已经有一套完整的状态机在跟踪结果——`待分配→已分配→执行中→待验收→已结案`，指派人（店长/HQ）在"待验收"这一步本来就要人工确认做得好不好，这**本身就是一种"回执"**，如果再加一层决策回执机制，等于同一件事被通知两次。决策回执存在的意义是**填补那些"批准之后没有人来验收、只能靠数据变化才知道有没有效果"的空白**（召回、推广这种），任务指派不属于这个空白。

**如果你觉得普通任务也需要"结果有没有达到预期"这层判断**（不只是"完成了没有"），这是可以做的，但需要另外设计——因为任务的"完成"和"有没有解决问题"是两件事（比如"整改后厨卫生"任务标记完成了，但下次桌访差评还是很多）。这个我建议先不在这次范围内，等 Phase 2/3 跑完再看要不要加。

## 7. 老实说——哪些角色还没问到位（你直接问了，如实列全）

红绿灯/决策回执/员工这三块，是因为你追问了才挖到"数字怎么算、卡片选哪几条"这种颗粒度。**其余角色目前还停在"知道要做哪个模块"的层面，没有到这个颗粒度**，一条条列出来：

### 7.1 老板——3条洞察卡怎么选

`closed-loop-report-service.js` 能生成的 `key_findings_for_owner` 理论上可能不止3条（每家店、每个问题都可能有）。**没定的规则**：
- 3条卡片从哪个池子里选、按什么排序？（我的建议：按严重度优先，同严重度按"预计影响金额"降序，这是我的推荐，不是确认过的规则）
- "问数据"的自然语言问答范围到底是什么——能答哪些问题、不能答哪些？现在只是复用已有 BI Agent，没有专门为老板场景定制过问法
- "周报"跟首页那3条卡是同一份内容的详细版，还是完全独立的一份周报？

### 7.2 总部——待审批/任务板/对比 三个模块的范围

- **待审批**：现有审批类型有请假、请款、奖惩等多种——总部工作台这里应该显示哪些类型？全部，还是只显示总部有权限决策的那几种？
- **任务板摘要**：显示"全部开放任务"还是"只显示高优先级"？跟老板首页那个红绿灯下面的"今天该处理的事"是不是同一批数据，只是老板看全租户、总部看自己管辖门店？
- **对比**：门店对比具体比哪几个维度？营收/毛利/人效/健康度（`store_ratings`）这四个都要，还是选一部分？

### 7.3 门店——"昨日经营"具体是哪几个数字

`daily_reports` 表字段很多——这个区块具体展示哪几个：营业额、客流、客单价、毛利率？还是店长最关心的可能是别的（比如跟目标的差距，而不是绝对值）？

### 7.4 总部HR——"考勤治理"和"人员流动"的具体判断标准

- **考勤治理**：显示哪些类型的异常——缺卡、迟到、请假未销假、加班超时？优先级怎么排？
- **人员流动**：这个板块具体算什么——在职人数变化、离职率（怎么定义分母）、还是入职/离职流水？
- **谁能被授予薪资权限**：目前设计是"给 hr_manager 角色的具体账号授权"，如果未来某个 store_manager 也需要看自己门店的薪资权限，这套模型支持吗？（现有权限组机制本身支持，但没确认过是否要开放这个场景）

普通任务人工改派（`reassign`）能不能派给任意人，还是有范围限制——这一点在 agents-service-v2 那个仓库里，我这次没法确认。如果这个对你重要，请告诉我，我下一步专门去查那边的代码给你准确答案，而不是猜。
