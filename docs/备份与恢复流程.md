### 2. 业务数据快照（应用层，非全库）—— `/opt/hrms/backups/`

- 脚本：`server/backup-state-only.sh`，每天12:00跑
- 内容：`hrms_state`表的JSON快照（gzip）、积分记录JSONL、薪资相关state切片
- 保留：14天（`HRMS_STATE_BACKUP_KEEP_DAYS`）
- **用途**：这是"业务逻辑层"的快照，不是完整数据库备份，用于快速核对/单独恢复某个租户的`hrms_state`，不能替代上面的PITR全库备份

### 3. 代码/部署备份（本次改造过程中新建的规范）

- 每次往生产scp覆盖`server/*.js`前，先备份到 `/opt/hrms/backups/pre-<改动描述>-<时间戳>/`
- `agent-service-v2`同理：`/opt/agents-service-v2/backups/pre-<改动描述>-<时间戳>/`
- 这类备份没有自动清理策略，需要人工定期清理旧的（否则会一直累积占磁盘）

### 4. 前端部署产物

## 二、⚠️ 最重要的发现：没有异地/云端备份

**核实结果**：`README_PITR.txt`标题明确写着"无 OSS"——WAL归档、物理基础备份、周/日逻辑导出、应用层state快照，**全部只存在这台服务器自己的本地磁盘上**。

**这意味着什么**：如果出现以下任何一种情况，现有的全部备份会跟生产数据**同时消失**：
- 这台ECS实例的磁盘损坏/数据丢失
- 阿里云该可用区发生影响这台实例的故障
- 误操作删除了整个实例（比如误操作释放了ECS）
- 服务器被入侵后攻击者删除了数据和备份

**这是当前灾备体系里唯一的"单点故障"级别的缺口**，其他备份机制本身设计得还不错（PITR体系相当专业），但都建立在"这台服务器本身还在"的前提上。

**建议**（不需要现在决定，先知道有这个选项）：
- 最低成本方案：把周度逻辑导出（`weekly_export`）定期拷贝一份到别的地方——哪怕是手动`scp`到你自己电脑，也比完全没有异地副本强
- 更完善方案：接入阿里云OSS，把周/日导出自动同步过去（`README_PITR.txt`里"周逻辑全库（可拷到 Mac）"这句话说明设计者本来就预留了"人工拷到本地"这个退路，只是现在没人在做）

## 三、恢复流程（按场景分类）

### 场景A：某个租户的hrms_state数据被误改/误删，需要恢复到某个时间点的状态

```bash
# 1. 找到最近一次的state快照
ssh root@47.100.96.30 "ls -la /opt/hrms/backups/hrms_state_*.json.gz | tail -5"

# 2. 下载到本地查看内容，确认是想要恢复的版本
scp root@47.100.96.30:/opt/hrms/backups/hrms_state_<时间戳>.json.gz /tmp/
gunzip -c /tmp/hrms_state_<时间戳>.json.gz | less

# 3. 确认无误后，手动UPDATE回对应租户的hrms_state（需要先备份当前值，防止二次误操作）
```

⚠️ 这一步目前**没有自动化脚本**，是手动核对+手动UPDATE，风险在于"确认哪部分数据要覆盖"需要人工判断，容易出错。建议：先在测试库验证一次完整流程，把这几条命令固化成一个脚本。

### 场景B：整个数据库需要恢复到最近一次逻辑备份的状态（比如整库损坏）

```bash
# 1. 在服务器上，用最新的逻辑导出创建一个新库验证（不要直接覆盖生产库！）
ssh root@47.100.96.30
sudo -u postgres createdb hrms_restore_test
pg_restore -h 127.0.0.1 -U postgres -d hrms_restore_test -c /opt/pg_pitr/weekly_export/hrms_weekly_<日期>.dump

# 2. 验证 hrms_restore_test 库里的数据完整性(核对几个关键表的行数、最新记录时间)

# 3. 确认无误后，才考虑真正切换生产库指向（这一步影响面极大，需要停机窗口+多人确认，不建议单人执行）
```

### 场景C：需要恢复到"某个具体时间点"（比如"故障发生前10分钟"），不只是最近一次周备

这是PITR（Point-In-Time Recovery）的价值所在，需要 **最新的base目录 + 之后连续的WAL文件**：

```bash
# 步骤概述（PostgreSQL PITR标准流程，需要在测试环境先演练过一遍再上生产）
# 1. 停止目标库（测试库，不是生产库）
# 2. 用 /opt/pg_pitr/base/base_<最近日期> 覆盖数据目录
# 3. 配置 recovery.signal + restore_command 指向 /opt/pg_pitr/wal_archive/
# 4. 设置 recovery_target_time = '故障发生前的具体时间'
# 5. 启动数据库，等待WAL回放到目标时间点后自动停止recovery模式
```

⚠️ `README_PITR.txt`原话："PITR 时间点恢复需：最新 base 目录 + 连续 WAL；生产演练前请在测试库验证。"——**这条流程从来没有真正演练过**，只是理论上配置好了。第一次真的需要用它的时候，如果流程有问题，会在真正的故障中才发现，代价很大。

### 场景D：代码部署错误，需要回滚到上一版本

```bash
# 找到对应的备份目录（本次改造期间创建的规范）
ssh root@47.100.96.30 "ls -la /opt/hrms/backups/ | grep pre-"

# 恢复对应文件
scp root@47.100.96.30:/opt/hrms/backups/pre-<描述>-<时间戳>/index.js /tmp/rollback_index.js
scp /tmp/rollback_index.js root@47.100.96.30:/opt/hrms/server/index.js
ssh root@47.100.96.30 "cd /opt/hrms/server && node --check index.js && pm2 restart hrms-service"
```

这条流程本次改造期间已经**实际验证可用**（部署新代码前的每一次备份+diff核对都是这个模式）。

### 场景E：整个服务器丢失（当前最大的风险敞口，见第二节）

**现状：没有可执行的恢复流程**，因为所有备份都在这台服务器本身上。如果发生这种情况：
1. 需要重新申请一台ECS
2. 从零搭建运行环境（Node.js、PM2、Nginx、Postgres）
3. **没有任何数据可以恢复**——除非碰巧有人之前手动把某份周备份拷贝到了别处

这是第二节提到的缺口在这个场景下的直接后果，也是灾备演练最应该优先针对性解决的问题。

## 四、建议的下一步（不需要现在都做，按优先级）

1. **（最高优先级）解决异地备份缺失**：哪怕只是每周手动把最新的`weekly_export`拷一份到本地Mac或者另一个云账号，也能把"场景E：整个服务器丢失=数据全没"这个最坏情况变成"可恢复，只是恢复到一周前"
2. **把场景A的手动恢复流程写成脚本**，减少人工核对出错的空间
3. **真正演练一次场景C（PITR时间点恢复）**，在测试环境完整走一遍，确认流程真的可行，而不是只是"理论上配置对了"
4. **给`weekly_export`/`daily_export`加自动清理策略**（现在`weekly_export`看起来没有自动删旧文件，长期会把磁盘占满）
