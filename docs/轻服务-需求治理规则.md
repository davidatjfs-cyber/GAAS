# 轻服务型 SaaS · 需求治理规则（Phase 0）

> 目标：商业化后防止「懂餐饮 + 懂系统」导致功能膨胀。研发优先级从「加功能」改为「降服务成本」。

## 1. 客户需求准入五条

| 判断 | 动作 |
|------|------|
| 单家客户需要 | **不做** |
| 可通过配置 / 规则 / 模板解决 | **配置解决**，不进研发排期 |
| 多数餐厅共有（≥3 家或明确行业共性） | 进入评估 |
| 能提升续费可见价值，或明显降低客服/上线/异常工时 | **优先** |
| 只是增加复杂度、特例逻辑、难维护口径 | **拒绝**，书面说明原因 |

拒绝话术模板：

> 该需求目前只服务单店场景 / 会显著增加系统复杂度，不符合托管交付标准。建议用现有配置项完成：____。若后续 ≥3 家客户提出同类需求，再进入公共能力评估。

## 2. 研发优先级（强制顺序）

1. 降低客服工时  
2. 降低上线时间  
3. 降低数据异常  
4. 降低研发介入  
5. 提高续费可见价值  
6. **最后**才是新功能  

任何「新功能」提案必须先写清：替代了哪类客服工时 / 缩短了哪一步上线 / 减少了哪类异常。写不清的不排期。

## 3. 谁有权说「不做」

- 客服 / 客户成功：可当场拒绝「单店定制」，记入需求池（状态=`rejected_single_store`）
- 产品 / 负责人：裁定「共有 vs 复杂度」
- 研发：发现会破坏通用口径或引入特例分支时，必须升级否决，不得私下接活

## 4. 与健康中心的关系

红名单（P0/P1）处理优先于一切新需求。客户提的「新想法」若不能降低红项或服务成本，默认排队到优先级 6。
